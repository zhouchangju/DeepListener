## 一、项目现状与核心价值分析

### 1.1 项目是什么

DeepListener 是一个**本地优先、单用户、BYOK** 的英语精听/影子跟读训练应用（Next.js App Router + SQLite/Prisma + ffmpeg）。核心用户画像：备考 TOEFL / 冲击 C1 的高阶学习者（作者本人即用户），重视隐私、处在网络受限环境。

### 1.2 核心价值闭环

```
上传音频/视频 → 转写并按词级时间戳切句 → 句级精听（波形圈选/盲听/变速）
→ 诊断"为什么听不懂"（ErrorTag）+ 收藏难句（Vault）→ 影子跟读 / 听写
→ FSRS-4.5 间隔重复复习 → Dashboard 数据化复盘
```

Track 状态机：`UNLEARNT → INTENSIVE → ANALYSIS → SHADOWING → SPEED_SHADOWING → PARAPHRASE → LEARNT`。

### 1.3 已具备能力（摘要）

- 转写 Provider 工厂（Deepgram / OpenAI Whisper / Google Gemini，undici 代理）
- 视频导入（ffmpeg 抽音轨）、内嵌字幕优先路径
- 波形精听（WaveSurfer）、Shadowing 零延迟内存切片、录音对比、听写逐词 diff
- 音标标注系统（重音/连读/弱读/吞音）
- Vault 难句库 + FSRS 复习队列 + 三种导出（音频包/Vault 文本/Library）
- Dashboard（学习时长/状态分布/记忆留存/复习表现/TOEFL 倒计时）
- 演示数据一键播种（/api/demo）、PWA 壳、next-intl 双语

### 1.4 关键断点与半成品（证据）

### 1.5 当前阶段判断

项目处于**桌面发行前夕**（`docs/desktop-client-prd.md`、`openspec/changes/desktop-first-distribution/`、`desktop:package` 脚本已就绪）。因此本轮需求筛选的主约束是：**止血 + 数据资产化 + 发行前置**，而不是铺新功能面。

## 二、当前项目最关键的三个问题

1. **核心练习数据全丢**：听写结果、跟读录音、播放进度全部纯内存态——产品最独特的"用户真实错误语料"100% 被丢弃，Dashboard 只统计时长和自评，无法回答"我哪里弱、有没有进步"。
2. **导入链路失败全损**：转写失败删文件、无重试、无进度、批量串行。转写是唯一依赖外部 API 的环节，也是失败率最高的一步，失败代价 = 重传 + 重付 API 费 + 重等 10 分钟。
3. **统计口径失真**：ReviewLog 占位字段不写、时长统计无空闲检测、编辑句子丢标注——Dashboard 的"数据化复盘"承诺建立在不可靠的数字上，且每次文本修正都在销毁用户的手动标注资产。

## 三、最值得实现的三个需求

1. **听写结果持久化（DictationAttempt）** —— diff 引擎已写好却零调用，落库是"练习越多系统越聪明"飞轮的地基，解锁错词聚类、自动归因、判分改进一切下游。
2. **转写止血：重新转写 + 失败不删文件 + 换 provider 重试** —— 证据最确凿、损失最直接、实现边界清晰。
3. **修编辑清空 formatting 的 bug** —— 一行修复，消除"改一个错别字丢 10 分钟标注"的最高频资产损毁。

## 四、暂时不应该实现的需求（明确记录，避免反复提起）

- **跟读 AI 评分 / ASR 对比**：无法衡量效果的 AI 功能典型；ASR 对非母语口语误判率高；依赖录音留存（P2）；成本最大。发行后再评估。
- **本地转写 provider（whisper.cpp）**：叙事动人，但模型分发/打包/调优是大工程，与桌面发行冲刺直接冲突。发行后再评估。
- **PWA 离线训练**：单用户本地应用，离线场景≈0。
- **内嵌字幕质量门**：场景窄，单用户对自己片源质量有数，语言检测属过度工程。
- **Category 死代码清理 / ReviewItem 双轨合并**：纯内部重构，顺手做，不占需求位。
- **生词本/词汇层**：todo 里的 P0，但属新产品面，与当前"止血+发行"主线弱相关，发行后单独立项。

## 五、项目当前阶段的产品方向建议

**先做"资产与止血"，后做"教练"。** 桌面发行前的正确顺序是：
1. 把已经在产生但被丢弃的数据（听写结果、播放进度、ReviewLog 占位字段）落库；
2. 把失败全损的链路（转写、导出）加上恢复能力；
3. 把用户已有资产（标注、Vault、FSRS 状态）做成可迁移的一等公民（发行硬前置）；
4. 发行之后，再用积累的数据做差异化壁垒：**归因驱动的个性化复习**（这是竞品无法复制的，通用精听 App 没有归因体系）。

## 六、需求机会分析（保留项，14 字段）

> 评分公式：综合 = 用户价值×3 + 问题频率×2 + 核心相关性×3 + 证据强度×2 + 差异化×1 + 可衡量性×1 − 实现成本×2 − 风险×1（各 1–5，成本/风险 5 = 最贵/最危险）

### R1. 听写结果持久化（DictationAttempt）—— P0，综合 51（5/5/5/5/4/5，成本3，风险2）

- **方向**：数据闭环 / 结果质量
- **目标用户**：每日听写练习的备考用户
- **场景**：用户在 DictationPanel 听写 50 句，想知道哪些句错得最多、accuracy 有没有进步
- **当前问题**：`compareDictationAnswer` 返回完整 wordDiff/missingWords/accuracy，但没有任何 API 调用，结果只存组件 state，关闭即丢
- **证据**：`src/components/feature/shadowing/dictation.ts`、`DictationPanel.tsx`（零 fetch）、schema 无 DictationAttempt 模型
- **建议方案**：新增 `DictationAttempt` 表（sentenceId、input、accuracy、missingWords/extraWords JSON、耗时、createdAt）+ POST API + 提交时落库；后续可接复习队列
- **用户价值**：练习数据从全丢变资产；唯一现成的"用户真实错误语料"
- **不实现的影响**：一切下游智能（错词聚类、自动归因、判分改进）永远无数据地基
- **成功指标**：听写提交落库率 100%；可按句查询历史 accuracy；4 周后可输出错词 Top N
- **实现成本**：小（1 表 + 1 API + 前端 1 个调用点）｜ **风险**：低（纯增量）
- **结论：P0**

### R2. 转写止血：重新转写 / 换 provider 重试 —— P0，综合 48（5/4/5/5/4/4，成本3，风险2）

- **方向**：核心流程 / 可靠性
- **场景**：Deepgram 超时或把带口音音频转砸，用户想换 Gemini 重转
- **当前问题**：转写失败即删文件报错；成功后无任何 retranscribe 路由；换 provider = 删 track + 改配置 + 重传 200MB + 重等 10 分钟
- **证据**：`upload/route.ts:147-151`；grep `retranscribe|regenerate` 零匹配；`upload-error.ts:30-35` 甚至建议用户"换 provider 再传"
- **建议方案**：失败时保留已落盘媒体并建 status=FAILED 的 Track（或记录）；新增 `POST /api/track/[id]/retranscribe`（可指定 provider），复用 `processFile` 的转写段；rawJson 记录 provider/模型
- **用户价值**：失败代价从"重传+重付+重等"降为"点一次重试"
- **不实现的影响**：每次转写失败都是双倍成本和 10 分钟级返工，冲刺期高频发生
- **成功指标**：转写失败→获得可用转写的总操作步数 ≤ 2；重复上传次数归零
- **成本**：中（复用现有函数，含 UI 按钮）｜ **风险**：低-中（需注意不破坏现有 Track/Sentence 关联，重转写应替换 sentences 事务化）
- **结论：P0**

### R3. 编辑句子文本不再清空 formatting 标注 —— P0，综合 48（4/4/5/5/2/4，成本1，风险1）

- **方向**：核心流程 / 结果质量
- **场景**：用户花 10 分钟标注连读/重音，发现转写错一个词，改正后标注全没
- **当前问题**：`ShadowingConsole.tsx:131` 保存文本时硬编码 `formatting: null`
- **证据**：上述一行代码
- **建议方案**：保存时保留现有 formatting；若文本变化导致偏移失效，最小方案是保留原标注并标注"可能偏移"，不做智能迁移
- **成功指标**：修改文本后 formatting 保留率 100%（偏移容忍）
- **成本**：极小｜ **风险**：极低
- **结论：P0**

### R4. 语料资产一体化导出/再导入 —— P0，综合 41（5/2/5/4/4/4，成本3，风险3）

- **方向**：竞争差异化 / 可靠性（发行前置）
- **场景**：换设备、或 Electron 桌面版落地时迁移全部学习资产
- **当前问题**：三个导出各自为政（音频/文本/Library），导入路径只有"上传媒体转写"；带 ErrorTag 和 FSRS 状态的库无法迁移
- **证据**：`src/app/api/library/export`、`/api/vault/export`、`/api/audio/export`；sync 脚本只 rsync 文件
- **建议方案**：单一 JSON 包（tracks + sentences + reviewItems + errorTags + reviewLogs + vault + 媒体文件清单引用）+ 导入端校验合并
- **成功指标**：在新机器导入后 due 队列、Vault 标签、练习进度与源机一致
- **成本**：中｜ **风险**：中（需处理 ID 冲突、媒体路径重映射）
- **结论：P0**

### R5. 播放进度记忆 + Dashboard"继续上次"入口 —— P1，综合 46（4/5/4/4/3/4，成本1，风险1）

- **方向**：高频痛点 / 核心流程
- **场景**：40 分钟课程分多次练，回来要手动拖波形找位置；每天打开应用要先想"我该干嘛"
- **证据**：`PracticeClient.tsx:78` shadowIndex 恒为 0；grep localStorage 仅 onboarding/i18n；dashboard 无 actionable 入口
- **建议方案**：localStorage 按 trackId 记录 shadowIndex + 播放位置；Dashboard 加"继续上次练习"卡片
- **成功指标**：重进 practice 自动定位到上次句子；Dashboard 一键续练
- **成本**：小｜ **风险**：低
- **结论：P1**

### R6. 听写判分等价归一化 —— P1，综合 48（5/4/5/4/4/4，成本2，风险2）

- **方向**：结果质量
- **场景**：用户听写 "their"（原文 "there"）、"2024"（原文 "twenty twenty-four"）被判错，信心受挫
- **证据**：`dictation.ts:15-56` normalize 仅小写/去重音/去标点
- **建议方案**：等价规则表（同音词、数字↔拼写、缩写展开）作为判分前的归一化层，规则表可测试、可扩充；不上 LLM
- **成功指标**：人工抽审误判率下降；"判错但实际可接受"案例在规则表覆盖后归零
- **成本**：小｜ **风险**：低
- **结论：P1**

### R7. 复习卡片一键跳回原句上下文 —— P1，综合 42（4/4/4/4/3/4，成本2，风险1）

- **方向**：核心流程断链
- **场景**：复习时听不懂某句，想放回原文听前后句——现在要手动找 track、拖进度条
- **证据**：`ReviewClient.tsx` 有 sentence.track.id 但无跳转；practice 页不读锚点参数
- **建议方案**：practice/[id] 接受 `?sentence=<id>` 锚点并定位波形；review/vault 卡片加跳转按钮
- **成功指标**：从复习卡到原句上下文 ≤ 2 次点击
- **成本**：小｜ **风险**：低
- **结论：P1**

### R8. 入库前转写校验 + 切分修复纯函数层 —— P1，综合 39（4/3/5/4/3/4，成本2，风险2）

- **方向**：结果质量 / 智能化（规则系统）
- **场景**：Gemini 幻觉出 end=9999 或 start>end 的句子，练习页 sliceAudioBuffer 直接抛错，整条素材报废
- **证据**：`upload/route.ts:126-146` 入库零校验；`google-provider.ts` 靠 prompt 乞求无重叠；`deepgram-provider.ts:57` 只看标点切句，长句不拆碎片不合
- **建议方案**：入库前纯函数 pass：时间戳单调性/越界修正、超长句（>25s）按词级时间戳在最长静音间隙二次切分、碎片句（<1s 且 <3 词）合并
- **成功指标**：入库转写 100% 通过校验；句子时长 3–20s 达标率可测；切片报错归零
- **成本**：中（纯函数+测试）｜ **风险**：低-中（改变切分会影响听写单元粒度，需保留原始 rawJson）
- **结论：P1**

### R9. 统计口径修复：ReviewLog 补全 + 学习时长空闲检测 —— P1，综合 39（3/4/4/5/2/4，成本2，风险2）

- **方向**：数据闭环
- **场景**：开着 practice 页吃饭 1 小时，"C1 进度 400 小时"注水；Dashboard 无法分析"盲听 vs 看答案哪个更容易 Again"
- **证据**：`review/grade/route.ts:23` 只写 rating，reviewType/duration 永远默认值；`TimeTrackingContext.tsx` 10 秒心跳无空闲检测
- **建议方案**：grade API 写入 reviewType/duration/倍速；前端心跳加空闲/无音频暂停检测
- **成功指标**：新 ReviewLog 字段非默认率 >95%；挂机不再计入时长
- **成本**：小｜ **风险**：低
- **结论：P1**

### R10. 归因加权复习队列（最小版）+ 标签自动补全 —— P1，综合 41/35（5/4/5/3/5/3，成本4，风险3）

- **方向**：差异化（主壁垒的种子）
- **场景**：Dashboard 告诉用户"60% 的听不懂是连读问题"，复习队列自动把连读句排前
- **证据**：ErrorTag 7 类归因体系已入库（多对多）、analytics 已按 tag 出图；但排程完全不看归因；标签自由文本导致 grammer/grammar 污染
- **建议方案**：最小版 = FSRS 队列在同等 due 条件下按 ErrorTag 弱点加权排序（不做自动归因）；标签输入改 datalist 自动补全已有标签
- **成功指标**：复习队列中弱点归因句子占比可配置/可观测；标签拼写变体归零
- **成本**：中｜ **风险**：中（加权逻辑需可解释、可关闭）
- **结论：P1**

### R11. 导出突破 500 段上限（分批导出）—— P1（条件触发），综合 39（4/3/4/5/3/4，成本3，风险2）

- **方向**：可靠性
- **场景**：冲刺期攒 800 个难句导出通勤听，被 "Too many sentences to export" 硬挡
- **证据**：`audio/export/route.ts` maxSegments=500、maxDuration 300s
- **建议方案**：不做全异步队列；前端按 500 段自动分批 + 合并下载（或 zip），失败批次可重试
- **成功指标**：800 句导出成功；无超时
- **成本**：中｜ **风险**：低-中
- **结论：P1（若当前曲库未逼近 500 段可缓至 P2）**

### R12. 转写重试 + 音频 hash 去重缓存 —— P1，综合 40（4/3/4/5/2/4，成本2，风险2）

- **方向**：可靠性 / 成本控制
- **场景**：失败重传后同一文件重复付费；429/5xx 无 retry
- **证据**：全库 grep `retry|backoff` 零实现；rawJson 不含 provider 标识
- **建议方案**：provider 调用层加 429/5xx 有限指数退避（≤3 次）；上传时算音频 hash，命中已有 track 直接提示复用
- **成功指标**：瞬时 429 自动恢复率；重复导入零重复转写调用
- **成本**：小-中｜ **风险**：低
- **结论：P1**

## 八、本轮实施范围建议（待审核确认，未实施）

**建议本轮实现 R3 + R1 + R2 三条（1 个 bug 修复 + 2 个 P0），理由：**

- R4（资产导出/再导入）虽是 P0，但工程量大且与桌面发行工作流强耦合，建议与发行 sprint 合并做，避免两个大工程并行。

- 假设当前阶段以"桌面发行前止血+数据资产化"为主线（依据：desktop-client-prd 存在且为 Active Initiative）；若用户认为应优先铺新功能面（生词本/AI 出题），P2 中的 #30/#14 可重新评估。
